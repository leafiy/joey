# sftp 走请求流水线,两个方向都暂存续传

原引擎的 sftp 读写是同步请求/应答:发一块、等一次服务器确认、再发下一块,吞吐被锁死在 `chunk / RTT`,与带宽无关(255 KB 块在 100 ms 往返下约 2.5 MB/s,200 ms 下约 1.2 MB/s)。这一直被归因为「没有 rsync 所以慢」,但 rsync 在传新文件时 delta 算法并不生效,它快是因为流式不等应答——真正的差距在流水线,不在算法。故用 libssh 0.11+ 的 `sftp_aio_*` 保持一批请求在途(按字节定窗,目标 8 MB),让吞吐由带宽而非延迟决定;这条路径对 Windows 远端尤其关键,那里没有 rsync 可回退。同时补上上传侧的暂存与续传:原先上传是 `O_TRUNC` 从零重写且无重试,断线即全废,而这正是 mac→win 唯一可用的路径。重试改为指数退避加抖动,并以「本次尝试是否真的推进了字节」为准回补预算,好让长文件在抖动链路上熬过去而不是把次数耗在一段坏路上。

**Consequences**: 远端目录会短暂出现 `.joeyupload` 暂存项目,开启隐藏文件时可见;网络失败留下的暂存项目由下次同名上传截断复用。窗口深度与 8 MB 目标是按常见 BDP 定的经验值,若实测下载提速明显弱于上传,瓶颈应查 libssh 的 SSH channel 窗口而非 sftp 层。引擎最低要求随之升到 libssh 0.11。
